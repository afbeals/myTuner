# Performance, efficient setup and Unraid validation

The owner selected implementation of the performance research, setup improvements and read-only Unraid checks. Performance means responsive playback/management and low interference with other containers sharing HDDs and RAM. The original measurements below describe the 0.2.2 performance work. Current integration is 0.3.0/schema 20 on `feature/ui-ux-overhaul`; the native TV project is also 0.3.0. Schema 19 supplies the compact persisted catalog after the schema-17/18 index/revision changes; schema 20 adds bounded session metadata and channel-creation retry identity. Nothing here authorizes source-media writes, new host tools, registry publication or household-container changes.

## Hardware and deployment evidence

Owner-provided baseline: **Unraid 7.1.2**, **Intel Core i5-12600K**, MemTotal **32,638,600 KiB** (about 31.13 GiB), MemAvailable **21,085,180 KiB** (about 20.11 GiB at that instant). This is shared host RAM, not a myTuner allocation. One Docker sample was all zero; the next showed **6.95% CPU**, **60.58 MiB / 31.13 GiB**, and **40.1 MB / 0 B** block I/O. Docker block I/O is cumulative, not a transfer rate. Neither sample proves the statistics reset/restart cause or establishes performance under load.

Media is on the existing HDD shares; playback cache uses `/mnt/user/transcoding/Transcode/mytuner`. Appdata/generated storage may also share HDD resources. Retain read-only media mounts, UID/GID 1000, the published TCP port and manual lifecycle preference. [Unraid checks](UNRAID_CHECKS.md) separates read-only checks from later disruptive rehearsal.

The initial synchronous implementation used a four-entry / 8 MiB encoded cache and a **64 MiB total raw-metadata / 100,000 authorized-item** admission guard. Those measurements above describe that checkpoint. It could reject realistic large metadata catalogs; the owner selected the replacement described below. Its 50k in-memory fixture began around 204 MiB RSS and peaked around 531 MiB, including fixture/SQLite/native allocations. Neither encoded cache size nor worker V8 heap settings are total process RAM limits.

### Selected large-library replacement

Schema 19 persists compact account-independent search/group records, memberships and coalesced dirty state. The main writer builds/updates records in yielded batches (64 rows / 4 MiB combined metadata input), preserving durable progress and publishing only a complete current revision. Production paged reads use one read-only worker. Grants and grouping are processed there; only the requested page crosses back. Full media/provider JSON is loaded for page hydration rather than every catalog entry on each search. The previous total-raw-metadata admission guard does not apply to this production path.

The compact authorized working set remains bounded at 64 MiB, individual compact rows at 256 KiB, returned pages at 8 MiB, and the worker has a 256 MiB old-generation / 16 MiB young-generation V8 setting. A single media record plus associated provider/display metadata must fit the 4 MiB batch-input budget. One reader, eight queued requests, 64 waiting callers, coalesced identical work, cancellation and a processing deadline prevent unbounded requests. These limits preserve explicit failure behavior; they do not guarantee HDD latency or total container RSS. See [large-library behavior](LARGE_LIBRARY.md) and final implementation measurements in [verification](VERIFICATION.md).

Two researchers independently investigated worker isolation and compact persistence. An 8k mixed file-backed prototype had about 49.67 MiB media JSON plus 40.40 MiB integration JSON; moving its existing aggregation to a worker reduced sampled main event-loop delay from about 798.5 ms to 1.48 ms, while RSS remained substantial. A separate 50k SQL prototype estimated compact tables/indexes around 34.7 MiB versus about 198.2 MiB raw tables. These are research prototypes, not final production or Unraid measurements. FTS was not selected: preserving exact substring behavior and its update cost require evidence.

## Setup flow and disk-cost boundaries

Source paths use cached Linux process mount metadata plus saved configuration. Candidates are container-visible paths, not reliable original host mappings; type/existence validation happens on selection/save, not by probing every mount on form opening. Non-Linux or restricted hosts retain manual entry. The application has no Docker socket and does not read Unraid flash configuration.

Sonarr/Radarr roots are observed from normal `/series` or `/movie` responses before no-file items are filtered. They can be inferred by the provider, so the UI labels provenance rather than promising every value is a configured root. Empty unused roots may need manual entry. Provider root-folder APIs can enumerate storage; ordinary modal reads do not call them. Choosing a saved connection is an explicit admin action, with exact provider/full normalized URL checks; no credential is returned to the browser.

An explicit **Check directory** action now validates a typed path and returns a small extension-based sample. It does no probing/provider requests/writes, skips symlinks and has entry/depth/directory/time limits; incomplete checks are not reported as empty. A timed-out underlying disk call retains admission until it drains. Changing a draft clears stale feedback.

Mapping preview uses cached inventory/catalog and explicit revisions. Lightweight root refresh does not fetch Sonarr episode-file inventories, so file-match preview needs a normal metadata inventory. Metadata roots mirror relative directories; caption subdirectory presets have different semantics. Changing a setting does not start a scan or write sidecars.

## Verification and cross-review

The pre-expansion checkpoint passed 344 backend tests, 92 browser journeys and 77 Darwin PNG comparisons. That performance checkpoint’s complete backend suite passed 421 tests, including the persisted projection, worker and directory resolver. Current 0.3.0 results belong in VERIFICATION.md. Final browser results are recorded in VERIFICATION.md. Three implementation agents then cross-reviewed other areas. Final combined counts/results belong in [VERIFICATION.md](VERIFICATION.md), not inferred from individual focused runs.

Corrections from that review include: source-write risk from symlinked generated parents after quota caching; shutdown turning paused jobs into terminal failures; stale collection membership during yielded scheduling; an NFO cache dropping explicit values equal to a filename fallback; status polling indefinitely pausing a recovery scan; and library pagination remaining past the last page after a refresh. Synthetic source-name/hash snapshots and descriptor/swap regressions cover the generated-path correction. No household source media was used.

Linux descriptor/publication behavior must pass container acceptance. Installed Mac FFmpeg supports the tested seekable descriptor protocol; unsupported implementations fail closed. Native Windows generation is not established; the intended Windows Docker workflow executes the Linux image.

## UI overhaul disk/read boundaries — 0.3.0

Catalog trees and selection/detail pages use the existing compact projection/read-only worker. Search is submitted explicitly rather than on each keystroke. Artwork pages remain 24 items and detail/tree pages default to 50. Mounted catalog views cache at most 24 response pages; shared directory trees cache at most 128 branch pages. Identity/view revision changes, recognized access failures and observed catalog revisions discard relevant cached presentation; unmount discards it. No next-page prefetch or source traversal is introduced. An explicit Refresh is available when a previously cached view needs current data.

The exact-video tray is capped at 5,000 IDs. Collection membership inspection reads compact IDs/revision, bounded to 5,001 rows for limit detection, and fetches member display rows in pages. Generation results accept bounded pages instead of returning every job item to paint its progress dialog. These changes bound hydration/response work; they do not make database reads or large selected sets free.

The explicit setup tree is a separate admin operation. It opens only permitted mounted/configured folders, lists direct child directories and never invokes ffprobe or scans video contents. One serialized lane holds at most eight cached listings; each returned page has at most 50 folders after examining at most 256 entries, with an 8,192-entry ceiling per listing and sixteen cached pages. Inactive handles expire after sixty seconds; no-link/storage exclusions, current authority and shutdown draining remain enforced. A capped/incomplete directory reports that state; manual entry/checking remains available. The typed directory resolver retains its independent small-sample bounds.

Staged settings do path validation once on an explicit save rather than saving every section separately. Unchanged saved mapping destinations may remain offline; newly changed destinations must validate and lead to the source without overlapping writable storage. Session last-used persistence is throttled and labels do not create a separate device registry. Actual Unraid HDD latency, other-container responsiveness and peak memory still require the existing target-host measurements; none of these UI/cache changes establishes that acceptance.

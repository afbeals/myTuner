# Content-only live programming guide: research and implementation plan

> Research proposal — implementation is pending owner selection. Recorded during the 0.3.1 follow-up; this document describes future behavior, not a delivered feature.

Research date: 2026-11-27. Repository: `afbeals/myTuner`.

This is a research/plan artifact only. No application, test, repository documentation, runtime data, or media was changed. No tests, servers, emulator, installation, network operation, commit, push, or deployment was run. Only source/documentation text and read-only Git status were inspected. The repository has substantial existing work in progress; implementation must integrate with that work rather than overwrite it. In particular, the profile-scoped library and main-page card work is active in the parent task.

## Confirmed outcome

The LIVE PROGRAMMING SCHEDULE VIEW should behave like a normal TV guide: one show/movie block per scheduled airing, using its original broadcast start and end. Its duration includes scheduled mid-roll commercials and the associated between-program break. During either kind of break, the guide continues to identify that break's owning show/movie. No commercial title, commercial artwork, separate commercial block, or continued-program duplicate should appear in that live guide.

Actual commercials still play, using the exact persisted intervals, offsets and shared broadcast clock. Player-specific Commercial/countdown/program-resumes information may remain. Paused/behind-live playback keeps its existing session timeline. The create-channel detailed preview continues listing the individual content/commercial intervals for scheduling review.

Example: program A runs 12:00–12:10, an ad 12:10–12:12, A continues 12:12–12:22, and A's following break runs 12:22–12:25. Program B begins 12:25. The live guide shows **A 12:00–12:25**, then B. At 12:11 and 12:24 it still shows A. Delivery still resolves the relevant commercial at those times. This is a presentation projection; it does not remove scheduled time or change scheduling policy.

## Recommended design: server-derived content projection

Use a small backend read-model helper, proposed `src/guide.ts`, called by the guide API. Do not independently reconstruct airings in browser and Kotlin, filter out ad rows in the clients, regenerate the schedule, persist a second timeline, or repurpose playback entries. A client-only helper cannot correctly identify an airing if its window starts during a mid-roll or trailing ad and the owning program rows are outside the returned window.

Keep the existing default `/guide` raw response backward compatible. Add an explicit optional `view=content` query projection; return a distinct `airings` array per channel rather than pretending that these are delivery `entries`. Current browser and native live-guide consumers move to `view=content` together with dedicated types. The old default remains available for old clients and technical consumers. Detailed draft/programming previews remain on their current raw APIs.

Suggested content contract:

```ts
type GuideAiring = {
  programId: string; // Stable identity within channel, retained across copied prefixes.
  mediaId: string; // Owning content media, never an associated commercial.
  title: string; // Effective display metadata for that content.
  startMs: number; // Full persisted broadcast bounds; not query-window clipping.
  endMs: number;
  available: boolean; // Owning program's scheduled fingerprint is valid.
  hasUnavailableIntervals: boolean; // Optional generic whole-airing warning.
  partial: boolean; // Only if retained/legacy data cannot establish full coverage.
};
type ContentGuideResponse = {
  view: "content";
  serverTimeMs: number;
  startMs: number;
  endMs: number;
  channels: Array<
    ChannelSummary & { error: string | null; airings: GuideAiring[] }
  >;
};
```

Finalize the small optional status fields before coding. Avoid `offsetMs`, raw segment IDs, commercial IDs/titles, or a fake `kind='program'`: these blocks are not delivery intervals. Use `(channelId, programId)` for UI identity. Do not use a copied schedule-entry ID, title, or media ID alone. No database migration is expected for the projection itself.

Compatibility: ship the server projection before a new native build; browser assets normally ship with that server. Old native builds continue using raw default behavior until upgraded. A new content client must validate `view`/`airings`; old servers currently ignore unknown query keys and would otherwise silently return raw data. Recommended: show the existing server-update recovery pattern for an unsupported projection, rather than use an inaccurate client aggregation fallback. A feature capability in `/api/health` is an optional additive alternative; avoid increasing API major version solely for this optional projection, because that would reject old TV clients unnecessarily.

## Projection algorithm and boundary rules

1. Parse existing window bounds and `view` with a validated enum. Preserve existing channel ordering, profile/PIN checks, subscriptions, archive/private visibility, and generic errors. Take server time once for the response.
2. Preserve the normal bounded `programming.ensure(channelId, endMs)` call; this existing GET may materialize coverage. The projection helper itself only reads persisted schedules and metadata. Never materialize historical or paused-only revisions to satisfy this guide.
3. After ensure, select the channel's active revision once. Select candidate **program IDs** whose entries overlap `[startMs,endMs)` using `entry.end_ms > startMs AND entry.start_ms < endMs`; candidates include commercial entries. Then join all entries in those revision/program groups using the existing `(revision_id,program_id)` index. Aggregate full bounds and resolve the first owning `kind='program'` media row. Do not aggregate only the already window-filtered rows, clip the API bounds, or query every historical revision.
4. Expose one row per valid owning airing. MIN(start) through MAX(end) includes every actual persisted mid-roll and trailing break. Never sum only content time or add configured maximum break durations. A content block may start before or finish after the requested window. Viewport layout, if any, may visually clip it while the data retains true bounds.
5. Authorize before projecting titles, artwork references, counts or response bounds. Preserve channel-level authority for upcoming scheduled members, including commercials, even though the content response contains no ad metadata. Recheck channel authorization after ensure when it has added members. Separately authorize the owning content row, including when that row ended before the requested window. If any protected group member would contribute disclosed aggregate bounds without permission, omit that group rather than grouping a filtered subset into misleading bounds. Never use the ad's readable metadata as a fallback for hidden owning content.
6. Batch-fetch distinct owning media and request-local authorizations. Use `createMediaProjector` for titles, and keep artwork/details tied to this same owning `mediaId`. Continue using the authorized media endpoint for focused artwork/overview, or add a bounded display summary only if measured worthwhile. Do not embed raw metadata/provider payloads in every guide block. Reset focused details/artwork on identity/profile/access changes; ignore delayed responses for the old identity.
7. Keep repeated airings of the same movie/file separate by program ID. Never merge by title, media ID, channel adjacency, series, or source duration. Do not bridge unexplained gaps or conflicting owner-media groups. Malformed commercial-only groups produce no named content block and a generic attention/coverage state; they must not expose a commercial tile or fabricate an owner.
8. Missing source files or fingerprint replacements do not change timing. Keep the authorized content title/media identity and bounds, with unavailable status. Recommended semantics: `available` describes the content; an optional `hasUnavailableIntervals` warns generically about any broken scheduled member, including an ad. An unavailable ad must not make its title appear in the guide or imply the whole movie has disappeared. Delivery continues to report the exact unavailable interval through its existing API.
9. Normal scheduler output and copied prefixes include whole airings. For legacy/truly incomplete retained groups, do not infer earlier ad time from source offsets or invent ends using media runtime/checkpoint state. Use only known persisted bounds, mark partial if completeness cannot be established, and show a generic partial-schedule indication. A group with no retained owner cannot become a titled content block. Checkpoints can validate a known end; they are rotation state, not a new title/artwork source. Commercial truncate/cutoff mode simply uses the already persisted shortened end.
10. Read only the active revision's authoritative prefix plus replacement future. A pending revision already contains both. Do not union the paused old revision, which could duplicate or contradict future airings. Keep session-context resolution in playback unchanged.

## Current/next, refresh and playback context

Share a small **selection** helper per client, not the aggregation algorithm: Current requires `startMs <= clockMs && clockMs < endMs`; Next is the next airing after Current, or the next upcoming airing if currently in a real gap. Do not label the first future block Now just because its end is later than now. An empty schedule and no next airing remain valid states.

Use one display-time sample per render/update. Return `serverTimeMs` so browser and native can anchor the guide's clock to server epoch time plus elapsed monotonic time. This maintains the same broadcast clock across devices and limits wall-clock skew. For native's custom browsing windows, use the estimated server now plus `guideShift`; correct/refetch a substantially skewed initial window after the first response. Preserve the one-hour TV window and navigation limits. Label a future window as upcoming rather than implying its first block is broadcasting now.

Advance display selection at the exact content-airing boundary, not at a mid-roll boundary or only at the next 30-second fetch. Keep periodic coverage/revision polling, with a boundary timer or a one-second lightweight UI tick. Do not make one-second guide network requests or regenerate the schedule for UI ticks. Refresh coverage near exhaustion and retain current focus/drafts during normal background responses. Handle background/sleep/resume by resampling time. Clear old profile/private details immediately on profile switch or 401/403/404; transient network errors may retain permitted stale data with the existing retry behavior.

Full guide and Browse channels show **live** channel airings while a player is paused or behind live. Opening, closing, focusing, or refreshing them must not change session position/revision/pause, call Join/Go Live, start a second player, or deliver another stream. The player's Now playing, ad countdown, content progress and Next continue to use its session descriptor. An explicit Watch live retains existing pause-discard wording/confirmation and joins live.

Native focus should survive ad boundaries because the program ID remains constant. Prefer an airing identity tag for content blocks and a same-channel/slot fallback when the former current airing expires. Retain navigation-action tags and `GuideNavigation.retainedTag` behavior; check both full guide and dialog lifecycle for stale artwork/network callbacks.

## Performance, safety and privacy limits

- Work is proportional to overlapping program IDs and their full segment groups in **one active revision**, not all retained history or the whole catalog. Reuse prepared statements, revision/time + revision/program indexes, batched media fetches, one request-local authorizer, and display projection memoization. Inspect `EXPLAIN QUERY PLAN`; use synthetic long airings, frequent breaks and large lineups to compare latency/rows/memory with the current guide. Avoid an arbitrary result truncation that silently removes Now/Next; if a measured limit is needed, expose explicit partial coverage.
- The current title projector can be nontrivial. Pass the distinct owning items once and do not load commercial metadata for content titles. Do not add per-block overview/artwork network prefetch or an unbounded cross-profile cache. Focused detail requests must be cancellable or identity-guarded; retained data must remain scoped to account/profile and current grants.
- No source reads/scans/probes, file copies/renames/sidecars, new conversions, media-server requests or new delivery should be necessary for projection. Use persisted metadata and fingerprints. Tests use temporary synthetic catalog data/media only. No real database, media, generated derivative, private path, token or signing key belongs in fixtures, logs, screenshots or Git.
- No scheduler policy, random selection, checkpoints, rotation, program ownership, delivery telemetry, paused-session retention or broadcast timestamps change. No parallel durable guide table or backfill is needed. Keep transactions short; do not wrap schedule materialization plus response rendering in a long write transaction. If a coherent snapshot is needed, take a short read snapshot after ensure.
- Network/media access, deployment, commit/push, and tool installation are separate actions and were not authorized by this research task. Do not resume emulator verification that `AGENTS.md` and `docs/differed.md` explicitly defer.

## Decisions for owner review

The core behavior is already selected by the owner: content-only live guide, breaks included in owning-airing bounds, actual commercials preserved, detailed create preview preserved. No additional confirmation is needed for those points when later implementation is authorized.

1. **Layout scope:** recommend correcting existing Now/next/Coming up blocks using Silver Signal. A horizontal multi-hour grid is additional product/design scope; approve it separately if that is what “normal TV guide” is intended to require.
2. **Title convention:** recommend effective content title as primary (episode/movie/general-video title), with series and S/E secondary where available. Native currently replaces focused titles with series names; align both clients. Series-primary instead is a reasonable explicit presentation decision.
3. **Which management preview:** recommend content-only for the live channel Coming up/Now-next lists, while create/edit draft interval previews remain detailed. If the owner wants another raw live diagnostic table, make it an explicitly separate management view rather than reintroduce ads into the live guide.
4. **Unavailable/partial wording:** recommend keeping authorized owning title and actual times, with a generic “Some scheduled content is unavailable”/partial-coverage indicator. Do not declare an entire movie unavailable because only one associated ad is missing; the player remains precise about the current interval. Final copy/status fields should be agreed in phase 1.
5. **Compatibility/verification:** recommend server-first optional projection and an update-server message for new clients hitting old servers; older TV clients require an app upgrade for this presentation change. Native emulator/device visual acceptance remains pending until the owner explicitly resumes it as separate follow-up work.

## Acceptance criteria

- Every live-guide surface displays at most one content block per channel/program ID and zero commercial/continued blocks. During a mid-roll or following break, the owning content title and artwork remain selected.
- Full persisted start/end bounds include actual inserted breaks, remain identical for narrow windows that overlap different parts of the airing, and align exactly with the next program's real scheduled start. No timeline time is removed, compressed or invented.
- Current/Next advance at the shared airing boundary, including pending-publication boundaries. Exact boundary selection is consistent on browser and TV; future windows and real gaps are represented honestly.
- Commercials still play with the same entry IDs/choices, durations, source offsets and commercial context; no pause, Go Live, subtitle, revision or delivered-exposure behavior changes. Browsing is passive until explicit Watch live.
- Private/unauthorized channels and owner media remain invisible, including through ads, artwork, counts and delayed refresh responses. Normal profile/PIN/subscription/source/subtree checks remain effective.
- Detailed creation/editing previews still show each scheduled commercial and resumed content row. Recently aired remains one row per completed authoritative airing with the existing bounded retention and no replay claim.
- Focus, draft retention, unavailable/empty states, long titles, desktop/mobile layout and native D-pad behavior have targeted evidence. Performance remains bounded without extra media I/O or a second schedule store. Any unrun native/device checks are explicitly deferred, not represented as verified.

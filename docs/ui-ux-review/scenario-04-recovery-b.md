# Scenario 04 — mistakes, interruptions, and conflicts · independent pass B

Review of the existing myTuner 0.3.0 browser build on 2026-11-26, using the installed Playwright Chromium and an isolated `e2e/server.ts --demo` fixture at `http://127.0.0.1:19307`. Signed in through the UI as the synthetic administrator and selected **Living Room**. This pass did not read pass A or other scenario 04 findings before the walkthrough.

**Result:** two P2 findings and one P3 recovery improvement. No P0/P1 issue was confirmed in this scope. Revision checks preserve configuration/profile/subscription/programming drafts, offline retry works, and real generation progress survives a browser reload. The basic **Edit source** dialog is the exception: its stale saves overwrite newer source values.

## Findings

### S04-B-01 · P2 — stale basic source edits silently overwrite newer settings

**Exact reproduction:**

1. On Sources, open **Edit TV shows** in two browser tabs before either saves.
2. In tab A, set Source name to `TV shows saved in tab A` and save successfully.
3. In tab B's still-open older dialog, set Source name to `TV shows stale draft` and save.
4. Both dialogs close with a successful save. The source now has B's value; no conflict or review action was offered.

**Expected:** detect that the source changed since B opened it, keep B's draft, and require a deliberate reload or review before replacing newer values. This follows the 0.3.0 plan's staged, revision-guarded source-dialog behavior.

**Actual:** both sequential PATCH requests return 200 with no browser-baseline revision in either payload. A later GET confirms B replaced A. This also means an editor changing one field submits the older values of the other fields in the form. No original media was changed in this reproduction.

**Evidence:** [request/response/readback JSON](/private/tmp/mytuner-scenario-04-b/source-stale-overwrite.json) and [final success screenshot](/private/tmp/mytuner-scenario-04-b/16-source-stale-overwrite-final.png). A 403 CSRF refresh appears transparently before one successful request; it is not the cause of the lost update.

**Code explanation after observing the UI:** [Sources.tsx](../../web/src/Sources.tsx#L264) sends name/root/kind/recursive without an expected revision. [server.ts](../../src/server.ts#L542) accepts those values without a browser revision. [source-management.ts](../../src/source-management.ts#L92) reads `before` when the save request starts; its comparison at line 127 catches changes during that request's async validation, but cannot detect that the browser opened its form before A saved.

**Recommendation:** include a source revision when opening the editor and require that exact revision atomically when saving. Reuse the programming editor's preserved-draft conflict actions. Cover the sequential two-tab case, not only concurrently executing server requests.

### S04-B-02 · P2 — save failures are hidden below the dialog's current scroll position

**Exact reproduction:**

1. Open the same source's **Configure** dialog in two tabs, initially scrolled to the top.
2. Change Subtitle folder names in both; save A, then save B.
3. At 1440 × 1000 or 390 × 844, observe B immediately after Save returns.
4. Manually scroll inside the dialog to its bottom to discover the conflict error.

**Expected:** a failed Save exposes a visible explanation and a recovery action near the initiating Save control, or scrolls/focuses a visible error summary.

**Actual:** the enabled sticky footer remains visible, but there is no visible error in the initial modal viewport. The actual alert begins at page y=1302.875 on the 1000px desktop viewport and y=1495.766 on the 844px narrow viewport, inside the clipped dialog body. Save appears to have done nothing. Connection failures from the offline and dropped-response runs use the same hidden position. The alert's `role=alert` helps assistive technology but does not make it visible to a sighted user.

**Evidence:** [desktop immediately after failure](/private/tmp/mytuner-scenario-04-b/17-error-outside-desktop-scroll.png), [narrow immediately after failure](/private/tmp/mytuner-scenario-04-b/18-error-outside-narrow-scroll.png), [same narrow dialog after manually finding the error](/private/tmp/mytuner-scenario-04-b/19-error-after-manual-scroll-narrow.png), [bounds](/private/tmp/mytuner-scenario-04-b/review-summary.json). These screenshots were visually inspected.

**Code explanation:** [ui.tsx](../../web/src/ui.tsx#L170) sets an error without moving focus/scroll, then renders ErrorBox after all form children at line 192. [SourceConfiguration.tsx](../../web/src/SourceConfiguration.tsx#L78) places Save in a separate modal footer, leaving the error at the end of the long scrolling form.

**Recommendation:** put a persistent error summary alongside the dialog footer or at the visible top of the modal body, focus it when a save fails, and keep field-specific detail beside the affected field. Include explicit conflict recovery controls there. Preserve the existing draft and error announcement behavior.

### S04-B-03 · P3 — lost committed response leads to misleading retry/conflict instructions

**Exact reproduction (synthetic network fault):**

1. In source **Configure**, change subtitle folders to `Subs, DroppedResponse` and choose Save.
2. Let the real PUT finish on the server using Playwright `route.fetch()`, record its successful 200 result, then abort delivery of that response to this browser only.
3. UI says “Unable to reach the server. Check your connection and try again.” Restore normal handling and press Save.
4. UI now says “Source settings changed elsewhere; reopen and review your draft.” A read-only GET confirms the intended draft was already saved by step 2.

**Expected:** communicate that the save outcome is unknown, offer a readback/reconciliation action, and recognize when the current server configuration already matches the submitted draft. Do not ask the user to infer whether another editor changed it.

**Actual:** the retry guidance leads to a conflict with the user's own successful prior save. The configuration dialog has no Load latest/review control; the available route is Cancel, confirm **Discard changes**, then reopen. The saved settings are correct and the stale revision check is correctly preventing an unsafe overwrite. This is a recovery/copy issue, not confirmed data corruption or a duplicate operation.

**Evidence:** [recorded successful commit and matching GET](/private/tmp/mytuner-scenario-04-b/dropped-response.json), [initial connection failure snapshot](/private/tmp/mytuner-scenario-04-b/04-committed-response-dropped.yml), [retry error](/private/tmp/mytuner-scenario-04-b/05-dropped-response-retry-conflict.png).

**Code explanation:** [api.ts](../../web/src/api.ts#L13) maps fetch rejection to a generic retry instruction. [SourceConfiguration.tsx](../../web/src/SourceConfiguration.tsx#L105) retains the old draft revision when it receives no response. [source-configuration.ts](../../src/source-configuration.ts#L95) correctly rejects that old revision on retry. Unlike [the programming editor](../../web/src/Channels.tsx#L1062), this dialog provides no explicit latest-versus-draft recovery UI. Profile and subscription conflict messages likewise refer to reload/review without a dedicated action in their dialogs.

**Recommendation:** distinguish “could not confirm whether Save completed” from a definite rejection. Offer **Check saved settings**; if the normalized current configuration equals the attempted values, acknowledge success. Otherwise show current and draft values with deliberate Load latest/Keep draft actions. Preserve revisions and avoid blindly resubmitting security-sensitive configuration.

## What worked well

- Revision conflicts kept source configuration, profile, subscription, and programming drafts intact. The tested conflicting changes did not silently replace the successful first tab's save.
- Programming has an understandable conflict banner, a deliberate latest-loading action, and a cancellable discard step. It is a useful existing pattern for the other editors.
- Offline failure retained form values and allowed successful retry when connectivity returned. Slow saves disabled controls and suppressed repeated mutation submission.
- Subscription removal warned about stopping current playback before attempting the guarded mutation. The administrator's visibility of another account's private synthetic channel was explicitly labeled and is permitted by the documented admin exception.
- Invalid directory checks explained the failure without removing the typed value. Browser Back/discard cancellation preserved the draft.
- Scan controls explain continued server work after closing. Generation is especially strong: the real running job survived a full reload, appeared in the active queue, and later exposed every completed output on narrow screens.

## Limits and cleanup

This was a local synthetic browser walkthrough, not Unraid acceptance. It did not test household media, unavailable mounted shares, a server restart during writes, long-running real scan cancellation, physical TVs, Android emulators, or install/update behavior. Password/PIN changes and session revocation were not exercised or classified as defects; their security-driven access changes may be intentional. This pass did not test a dropped channel-creation response or programming's Keep draft comparison branch.

The isolated demo was stopped through its owned shutdown handler; the browser/context and driver exited. Port 19307 refused a connection on cleanup verification. Both identified review fixture roots (`mytuner-ui-VemLs1` from the interrupted harness and `mytuner-ui-otwMNL` from the completed run), including their synthetic media, SQLite data, and generated outputs, were absent after cleanup. No unrelated process or temporary root was stopped or removed. Review evidence and temporary harness files remain under `/private/tmp`; no executable was downloaded or installed. No product fix is included.

## Save and deletion decisions

One Save needs a shared draft for name/owner, PIN intent, account grants and source grants, field errors and dirty-close handling. Current PATCH/PUT/POST/DELETE operations are separate commits: merely calling them sequentially cannot provide atomicity. Decide atomic batch API versus explicitly reported partial outcomes. For atomicity, validate/hash PIN outside the short transaction, reauthorize before commit, add conflict protection, then refresh all affected summaries. Preserve admin-only account/source/identity editing; authorized editors currently get PIN management. PIN changes clear profile unlocks (`src/identity.ts:132`). Do not interpret untouched blank PIN as removal.

Deletion dependencies include profile_accounts, source_grants, subscriptions, playback_sessions, profile_unlocks, schedule_revisions and problem_reports foreign keys (`src/database.ts:20,28,47,83,93,103,133`). These do not all cascade. Channels/collections belong to accounts; schedule renewal may rely on the deleted profile’s grants. Decide blocking versus migration/retention, history/report treatment and restoration before implementation. Define active playback invalidation and stale selected-profile recovery. Device pairing/account sessions are account-scoped; deleting a profile should not silently imply account-wide revocation. No deletion policy was selected.

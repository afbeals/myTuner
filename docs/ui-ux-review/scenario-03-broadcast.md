# Scenario 03 — editing an active broadcast with a paused viewer

Reviewed 2026-11-26 against the existing myTuner 0.3.0 `web-dist`, using installed Playwright/Chromium and the unchanged `e2e/server.ts --demo` fixture on `127.0.0.1:19305`. Review only: no product, test, baseline, build, dependency, or Git changes. Only this report is added to the repository.

**Result:** the requested edit/publish, program/break boundary, retained paused revision, resume, Go Live, and channel-switch paths passed in the browser. Three P3 clarity/state-consistency findings; no P0, P1, or P2 defect established in this scenario.

## Setup and evidence

- Signed in through the UI as the synthetic administrator and chose Living Room. Two independent browser contexts watched the same After School channel; a third page provided the editor. The editor shared the first context's account cookie but had its own page/profile selection. Browser contexts represent separate browser device sessions, not physical TVs.
- Used the fixture's existing 12-second The Last Platform, 8-second Maple Street, and 12-second Synthetic-ad. No clock acceleration, custom media, API writes, or database preconditioning. The fixture had no saved collection, so created `Scenario 03 Fixed` through the UI before selecting it in saved-channel programming.
- Actual mutations were performed with rendered controls. Read-only playback/API responses and video element state verified outcomes after the UI actions. No source media was touched.
- Artifacts: `/private/tmp/mytuner-scenario-03/`. Screenshots were opened with `view_image` at desktop 1440×1000 and narrow 390×844; narrow captures include both full-page content and true viewport captures. Full-page modal screenshots include background content and should not be mistaken for the viewport composition.

## Findings

### S03-01 — P3: resumed playback still describes itself as live

**Expected:** after Resume, explanatory copy agrees with the visible lag and describes continuing from the retained position; Go Live describes the explicit jump to the current airing.

**Actual:** the badge said **“199 Seconds Behind Live”**, the sidebar said **“3 min 19 sec behind live”**, and read-only state confirmed the original revision with `behindLiveMs: 199123`. The program details simultaneously said **“Watching this channel’s live timeline.”** In the edit-during-pause scenario, this can obscure that the viewer is still following the earlier revision.

**Evidence:** `11-behind-live-narrow.png`; `retained-session.json`. Source inspection only after reproduction: `web/src/Player.tsx:964` chooses that sentence for every non-paused state, without checking lag.

**Recommendation:** use the same lag state for the details paragraph and badge: for example “Playing from your saved position, 3 min 19 sec behind live. Go Live joins the current airing.” Keep the existing good paused explanation.

### S03-02 — P3: collection summary count stays stale after saving membership

**Expected:** after saving membership, the open collection's heading summary and video table describe the same saved contents.

**Actual:** after adding a second video, the table and pagination showed two while the open summary still said “Saved collection · 1 videos.” Reproduced in the opposite direction at desktop: removed Maple Street, then the summary still said **“Saved collection · 2 videos”** above the single The Last Platform row and **“1–1 of 1.”** The mismatch persisted after loading completed. Closing and reopening corrected it.

**Evidence:** `13-collection-count-stale-desktop.png`, `collection-count-stale.txt`; earlier narrow state in `10-collection-count-stale-narrow.png`. Source inspection: `web/src/Library.tsx:713` renders `selected.detail`; the membership save handler at approximately line 1072 refreshes library/detail data but does not replace that selected summary.

**Recommendation:** reconcile the open selection's summary after a successful membership save, or derive its count from the refreshed detail response. Use singular “video” for one. Keep the current selected collection open and preserve table position where possible.

### S03-03 — P3: paused channel-switch confirmation omits the destination

**Expected:** the confirmation identifies the new channel and makes clear that its live airing will replace the current paused position.

**Actual:** selecting **Scenario 03 Switch** while paused on **After School** displayed **“Watch live?” / “Watch this channel live and discard the current paused position?”** The background still showed After School and the select's committed current channel; the dialog never named Scenario 03 Switch. Cancel and confirm both behaved correctly, but “this channel” is ambiguous at the point of commitment, especially on narrow screens where the selector is offscreen.

**Evidence:** `14-switch-confirm-narrow.png`; corrected read-only outcome in `switch.json`. Source inspection: `web/src/Player.tsx:273` uses the same unnamed confirmation for `tune(id)`.

**Recommendation:** interpolate the destination label, for example “Watch Scenario 03 Switch live? This leaves your paused position on After School.” Retain the current Cancel behavior and explicit discard warning.

## Positives

The saved-channel editor separates Content, Commercials, and Preview; unpublished edits are protected; publishing requires a current draft preview. Both tested publication boundaries respected the current program and its associated break. Commercial cutoff previews exposed actual shortened durations, and the live sequence agreed with those durations after the recomputed activation time. Pause retained a useful picture and context without keeping media delivery active; Resume, Go Live, and switching affected one browser session. The narrow layout kept essential actions readable and reachable without horizontal page overflow in the inspected states.

## Limits and interpretation

- Collection edits change selection membership. They do **not** retroactively replace exact entries in an already-materialized schedule revision. This review does not classify the continuing Maple Street assignments as a failure; a newly generated preview/new channel correctly resolved the changed membership. No test waited for the entire pre-generated rolling window to expire.
- Browser sampling every 500 ms established ordering and full planned intervals; it is not frame-accurate AV continuity measurement. Some joins/boundaries briefly showed the previous frame or “Joining your channel…” while media was reattached. No physical TV, remote, emulator, native-app, long pause, restart, or original-media acceptance is implied.
- Automatic UI requests included CSRF 403→successful retry during shared-cookie multi-tab activity; these did not visibly block the tested actions. Login's unauthenticated 401s were expected. Two 404s were caused by the review helper reading an old resource-timing URL after its buffer filled; final switch verification used current polling URLs instead. These helper 404s are not product findings. `browser-events.json` preserves the trace.
- Code was inspected only after UI findings, for focused recommendations. No fixes, tests, baselines, installs/downloads, rebuilds, Git mutations, or original-media operations were performed.

## Ranked bugs and additional UX

- **ACC2-01 — P2, bug.** Manage sam → change role from editor to viewer without saving → enter a new password → Reset password. Password PUT succeeds and **closes the whole modal**, silently discarding the role draft; reopening shows editor. Only the password request was sent. The reverse direction is also structurally possible: both independent forms close selected account on success (`web/src/Management.tsx:129–168`). Preserve the other form’s draft, or warn before an operation closes/discards it. A single Save contract is a product decision: password reset and role/security updates can fail independently and invalidate sessions. **Accept:** successful/failed action in either section never silently loses another dirty section; deliberate Cancel explains what is discarded.
- **ACC2-02 — P2, bug/additional UX.** Saving the current administrator’s unchanged account form revokes its sessions, and the next reload returns Sign in. The UI only explains session revocation next to the Disable checkbox and password reset, so **Save account** is unexpectedly disruptive. `src/identity.ts:105–111` unconditionally revokes all account sessions for every update. Do not revoke on a no-op; show consequences for real role/disable changes and immediately communicate self-sign-out when it is required. **Accept:** unchanged Save causes no access/session change; intended security changes clearly explain whose devices will sign out and route the current browser coherently to reauthentication.
- **ACC2-03 — P2, additional UX.** At 390px the initial table shows Account/Role but hides Status/Manage to the right; keyboard activation of Manage scrolls to Actions and hides account identities instead. Long/disabled capture shows only Status/Actions, leaving repeated “Manage account” buttons visually unassociated with their usernames. This is bounded horizontal scrolling, **not document overflow** (`web/src/styles.css:1197` imposes 38rem table minimum). Use stacked account cards or a sticky identity column with a clear scrolling cue. **Accept:** username, role, status and its management action remain visibly related at 390px and 200% text; keyboard focus is visible, including long names.
- **ACC2-04 — P3, additional UX.** Create/manage success closes the modal without a named success message; Revoke all sessions stays in the modal and offers no explicit acknowledgement after its request. Provide concise accessible “Account saved”, “Password reset; devices signed out” and “Sessions revoked for [name]” feedback. Keep pending buttons stable and prevent duplicate action. **Accept:** keyboard/screen-reader users can distinguish success, failure and cancellation without inferring it from disappearing content.

## Owner items

**ACC-01 — confirmed gap, P2 owner request.** Create and reset each expose a single password field; reset was successfully submitted without matching confirmation. Add Confirm new password, matching validation before request, no paste restriction, and an accessible optional show/hide control. Keep the ≥12-character rule visible before errors rather than relying solely on browser validation. Creation confirmation is the same shared pattern if the owner wants consistency. **Accept:** mismatch cannot submit, correction preserves the first field and nonsecret draft, both inputs use new-password autocomplete, errors identify the field, and successful reset states revocation consequences.

**ACC-02 — P3 owner request.** Revoke all sessions is detached below the two form cards, especially on narrow screens. Move it beside the relevant Save action as a secondary explicit security action, while keeping Reset password semantically separate unless one atomic save is approved. Red danger text already distinguishes revocation; do not give it primary prominence. **Accept:** Save/Revoke have distinct labels, logical tab order and usable wrapping; revocation does not imply saving a dirty role/password draft.

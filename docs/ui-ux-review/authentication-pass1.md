## Current behavior and owner coverage

Account login works with labeled username/password fields, password-manager autocomplete and native required-field validation. Incorrect credentials stay in the form with an alert. Successful login opens Channels with the alphabetically first permitted profile selected; it does not show an initial “Who’s watching?” choice. A protected profile gates Channels, Library, Subscriptions and Watch TV. An editor entered a wrong PIN, saw “Incorrect PIN”, then successfully unlocked with the correct synthetic PIN. Reloading the same browser session retained that unlock. Browser administrators bypass profile PINs; this is deliberate server authorization behavior, not a failed PIN implementation (`src/security.ts:224`).

The first-administrator screen is explanatory, not an account-creation form: an administrator must be bootstrapped on the server. No production bootstrap or native device startup was attempted. A delayed mocked `/api/auth/me` demonstrated “Connecting to your network…”. A mocked 503 showed the sign-in form plus the server error. A mocked empty profile response displayed “Create your first profile” and a Profiles link. These three are injected UI states, not fixture/server failures.

Applicable global requests: **GLO-01** applies to the profile picker (existing dialog has Close and keyboard focus containment, but no footer action is needed for immediate choice); **GLO-03** applies to the authenticated navigation (current labels are capitalized; initial landing/priority remains a product choice); **GLO-04/05** apply to setup and PIN explanations; **GLO-06** applies to Switch profile/Unlock hierarchy; **GLO-08** is confirmed below. **GLO-10:** no CSP style violations appeared; 401/403 were expected authentication failures and 503 was deliberately mocked. **GLO-02/07/09/11** do not apply to this page. ## Ranked findings

- **AUTH1-01 — P2, bug / GLO-08:** After entering credentials (including a failed sign-in), clicking “Server and TV setup instructions” opens a browser confirmation: “Discard unsaved form changes? A request already received by the server may still finish.” The shared Form draft guard treats credentials as an editable configuration draft (`web/src/ui.tsx:134`, `web/src/navigation.ts:4`; sign-in adoption `web/src/App.tsx:167`). This makes the recovery/help path feel destructive. Exempt ordinary credential entry from configuration-draft prompts; if an actually pending request needs a guard, give it an accurate app-owned prompt. **Accept:** typed or rejected credentials can navigate to setup help without a browser confirm; genuine configuration drafts retain protection; browser-owned tab-close prompts remain browser-controlled.
- **AUTH1-02 — P2, additional UX:** PIN entry has no visible 4–8 digit requirement or recovery guidance. The browser pattern supplies the rule but its generic validation message cannot explain why this profile needs a PIN or who can help (`web/src/App.tsx:398–424`). Wrong-PIN feedback is clear and visually legible. Add concise “4–8 digits” guidance and “Ask the profile owner or administrator if you forgot it”; keep the protected profile name and Switch profile action visible. **Accept:** the requirement is visible before typing, associated programmatically, and users can choose another profile without losing their account session.
- **AUTH1-03 — P3, additional UX:** The injected startup failure renders below the normal login/help content with no Retry connection action. It looks like a login problem even though identity loading failed (`web/src/App.tsx:87–100,155–162,210`). Offer an explicit connection-error state with Retry and setup help, avoiding an unnecessary password re-entry. **Accept:** restoring the endpoint and choosing Retry recovers the existing session; signed-out users still receive ordinary sign-in.

No P0/P1, privacy disclosure, horizontal overflow or CSP breakage was observed in this bounded review. Missing broad authentication/security penetration coverage is not evidence of correctness.

## Shared work, adoption and decisions

Global construction: configurable draft guarding/app confirmation (GLO-08), consistent connection-error/retry presentation, accessible contextual help. Page tasks remain explicit: **apply credential-specific guarding to sign-in and unlock**, **apply retry presentation to startup**, **apply concise input/recovery guidance to TV PIN**. Preserve Silver Signal colors, large controls and clear error contrast.

Decide whether browser sign-in should first ask for a profile or intentionally select the first profile, and whether an unlock should survive a browser reload. Current API startup clears unlocks on explicit login; browser reload only restores identity (`src/playback.ts:46`, `web/src/App.tsx:179`). Do not silently impose native fresh-launch policy on every browser reload. Viewer empty-state wording should depend on permission: an administrator can create profiles; a viewer normally needs an administrator.

## B-01 — P2: viewer invests in a channel draft that is denied only at preview

**Repro:** Admin creates a Viewer and grants Watch on Living Room without Manage. Sign in as viewer, unlock profile, open My Network → Create channel. Enter a name; Next → Add content group → Orbit Patrol → Use selection → Next → Next → Generate preview.

**Expected:** Watch-only users receive a watching-oriented entry point. Creation should be unavailable with a clear explanation before asking for draft work. If available management depends on selected profile, say that and provide a useful way to choose a manageable profile or contact an administrator.

**Actual:** Active creation buttons launch a complete four-step editable wizard. Only the final preview rejects the operation with `403 {"error":"Profile management not allowed"}`. The wording does not explain the Viewer role, required Manage access, or next action. No channel was created: this is an affordance/recovery defect, not a demonstrated privilege escalation.

**Evidence:** 05-viewer-network-narrow.png, 06-viewer-create-narrow.png, 09-viewer-preview-denied-narrow.png and viewerWizardDenial in authorization-evidence.json. Narrow layout itself remains readable with visible navigation/action buttons.

**Recommendation:** Gate creation and programming actions using effective account/profile management capability; show concise read-only guidance. Apply consistently to header actions and tray actions. Retain server checks. After observing the issue, source inspection found unconditional creation buttons in web/src/Network.tsx:31 and web/src/Channels.tsx:191; use those as review starting points. Create collection was visible but its full save path was not exercised.

## B-02 — P2: revoked playback retains live status and gives opaque retry errors

**Repro A:** Admin subscribes the owner's private channel to Living Room. Owner watches it there. Admin unchecks it in Profiles → Living Room Subscriptions → Save subscriptions, then explicitly confirms Save lineup.

**Repro B:** Sam watches After School on Living Room. Admin opens Manage Living Room, removes TV shows from Allowed library and saves.

**Expected:** Stop unauthorized playback, refresh permitted channel choices, explain neutrally that the channel is unavailable for this profile or access changed, and offer a guide/profile action. Live/Pause and retry should reflect the terminated state. Retained details should not imply delivery continues.

**Actual:** Enforcement works: the video pauses, old sessions fail, and freshly requested source metadata/file bytes are denied. UI overlays raw “Playback session not found” (A) or “Channel not found” (B), while still showing LIVE, Pause, prior episode/next-program details and Retry playback. The source-revoked player initially still lists After School as selected; retry does not repair permissions.

**Evidence:** 14-subscription-revoked-settled.png, 15-source-revoked-playing.png, 16-revoked-retry.png and authorization-evidence.json. Video state after each revocation was paused. Previously displayed titles and the buffered synthetic picture are stale client state, not newly disclosed unauthorized metadata. Fresh sam requests to private programming, revoked media metadata/file and old source session returned 404; revoked library contained no show/movie/folder entries.

**Recommendation:** Treat session/channel loss as an unavailable playback state. Reconcile guide and current selection, stop the active-looking status/controls, use neutral user-facing copy, and prioritize returning to permitted guide/profile choices. Reserve Retry for recoverable delivery failures. Post-observation inspection shows failure-triggered retry and LIVE fallback in web/src/Player.tsx:911–931, which are useful starting points.

## Positives and limits

Private account ownership stayed independent of shared-room subscriptions. Admin was the observed sole cross-owner discovery exception. Owner versus watch-only management controls were distinct. PIN error/retry and forgotten-PIN guidance were clear; fresh sign-in did not inherit another account's unlock. Revocations were enforced by the server, and profile/account changes cleared the selected player/private preview.

This was a focused interactive review, not exhaustive API fuzzing. The private channel used the same synthetic TV source as the shared channel, so permitted access to those same media bytes alone cannot demonstrate private-channel disclosure. The browser negotiated direct MP4; private HLS manifests/segments were not exercised. No native TV/emulator acceptance was attempted. Explicitly assigned editor Manage was not toggled on in this pass; implicit owner/admin Manage and assigned Watch-only behavior were exercised. Exact-video tray selection across profile changes, subtree-specific grants, long PIN lockout and every private count/search/preview endpoint remain unverified. The #accounts API path initially guessed during read-only exploration was nonexistent and is excluded from authorization evidence.

# Scenario 06 — background generation and scanning while browsing or watching

Review of the existing myTuner 0.3.0 browser build on 2026-11-26. **One verified feedback defect affects both generation and scanning:** work paused behind playback is described as running/processing. Bounded actual generation, cancellation, retry, reload recovery, and existing-output reuse otherwise worked in this walkthrough. Findings are approved for subsequent correction; this report does not select severities or implement fixes.

- Isolated server: `http://127.0.0.1:19309`; synthetic administrator `designer`; profile Living Room. Existing HEAD is `a67d418`; the reviewed working tree and built browser contain additional in-progress work, so that SHA alone does not identify the reviewed build.

The fixture contains 8,338 real temporary hardlink paths to one synthetic 120-second, 160 × 90, 1fps video, 137 root directories, 128 folders with at least 64 files and paths six directories deep. ## S06-01 — playback-paused work is labelled as running and processing

**Verified observation.** The global page notice correctly reports that optional work is paused for playback, but the job-specific controls describe a file as actively processing. The notice sits outside and behind the progress dialog. Scan controls have the same mismatch.

Exact reproduction:

1. With ordinary automatic maintenance/playback admission enabled, play a permitted channel in one tab. Verify video is advancing.
2. In a second tab, Generated Assets → choose a small folder → select outputs → Preview scope → Start generation.
3. Keep playback running and leave Generation progress open for more than five seconds.
4. The dialog reports `running · 0/6 outputs completed · 0 failed` and `Processing: Needle - Fireflies.mp4`. The Active queue card says Running. Behind the modal, the page notice says work is paused while someone plays video.
5. Read-only verification shows `active:null`, `waiting:1`, `paused:true`, `admitted:0`, `completed:0`. No optional generation has been admitted. Actual playback samples are `paused:false`, `readyState:4`, with currentTime advancing 45.657515 → 60.19001.
6. While that video remains playing, start a source scan. Background waiting becomes two, still with zero admitted. The source and dialog say “Scan in progress…” and “Scanning this source. You can close this dialog; work continues on the server.”

**Why this is a confirmed UI defect:** the user sees an unchanged file apparently processing when the server has deliberately deferred all work. This makes a healthy playback-protection policy look stalled and can encourage unnecessary cancellation or repeat scans. The correct global notice helps, but does not make the dialog's file-specific statement true.

**Evidence:** [paused generation screenshot](/private/tmp/mytuner-scenario-06/19-paused-labelled-processing.png), [concurrent Watch screenshot](/private/tmp/mytuner-scenario-06/20-watch-during-paused-job.png), [queued scan screenshot](/private/tmp/mytuner-scenario-06/22-scan-queued-playback.png), and [exact observation transcript](/private/tmp/mytuner-scenario-06/paused-processing-proof.json).

**Delay non-causality:** phase 2's temporary 2.5-second delay only runs inside a generation callback after background admission. The observations above have `admitted=0`, so the injected callback has not run. The pause is caused by actual playback and the ordinary server policy; it was not synthesized by changing a status response or forcing a paused flag.

**Code explanation after observing the UI:** [generation.ts](../../src/generation.ts#L442) marks the job running and [line 450](../../src/generation.ts#L450) marks its first item running before awaiting `background.run` at line 456. The job query treats that item as current. [Management.tsx](../../web/src/Management.tsx#L475) renders the raw status and converts any current item into “Processing.” [Sources.tsx](../../web/src/Sources.tsx#L55) locally sets the scan running as soon as the request is submitted, before admission. [BackgroundStatus.tsx](../../web/src/BackgroundStatus.tsx) has the correct global pause state but it is not included in either task dialog.

**Recommendation:** give queued/admission-waiting/paused work an honest task-specific state. Put “Waiting while video is playing; resumes automatically” inside progress and scan dialogs, and show “Processing” only after actual admission. Keep cancellation available while waiting and distinguish that state from encoder-capacity waiting. Preserve the correct global notice and the successfully observed automatic resume behavior.

## Positive behavior and small refinements

- Scope is explicit and independently controls recursion, output types and replacement. Large requests are bounded before creating jobs. The preflight's unknown time/size statement is honest.
- Cancellation explains preservation of completed work and leaves item-level results. Retry and reload recover the real job rather than creating a replacement job.
- Existing-output reuse was verified through unchanged output sizes and modification times, not just a label. Actual generation stayed outside source roots.
- Browse/file-search and Watch remained usable in the observed local cases. While playback was active the scheduler protected it by admitting no optional filesystem work; after pausing playback the queued scan and generation completed.
- Desktop and narrow dialog layouts remain readable with long nested paths and a visible footer.
- Refinements, not additional confirmed defects: disclose the 5,000-file cap before Preview scope; distinguish reused versus newly rendered outputs in completed results; use a direct “Cancel unfinished work” confirmation action instead of generic “Continue.” The plan does not establish that these refinements are required behavior.

## Limits and cleanup

This establishes local UI/lifecycle behavior only. It does **not** accept Unraid shared-HDD throughput, shared RAM/CPU interference with household applications, cold probing, heterogeneous codecs, high-bitrate streams, unavailable mounts, long encoder contention, or server-crash/restart recovery. The actual encodes were tiny and the controlled overlap used an explicit delay. Source originals, source fingerprint/settings invalidation, output corruption, storage exhaustion and incomplete-output serving were not independently fault-tested. No speculative claim about those paths is a verified finding.

The first title-only search was inappropriate for the fixture's folder-oriented catalog; the intended file-name mode later returned all four expected matches. Some initial automation locators used visible button text rather than its accessible name; these were harness locator errors, not vanished dialogs or product failures. The first phase-2 browser attempt preceded server readiness and received connection refused; it was retried after readiness, without changing product code.

Both isolated browser runs were explicitly closed, and both owned servers completed their shutdown handlers. Port 19309 refused connections afterward. Both fixture roots, including synthetic media, SQLite data and generated outputs, were absent; no owned fixture/driver or source-root-matching FFmpeg/ffprobe process remained. See [cleanup verification](/private/tmp/mytuner-scenario-06/cleanup-verification.json). Review PNG/JSON evidence and temporary harness files remain under `/private/tmp`; the shared fixture was preserved. Only this report was added to the repository.

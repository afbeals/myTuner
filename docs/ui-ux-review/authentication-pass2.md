## Workflow and observed states

Empty fields use browser required validation. Wrong password displays an alert “Invalid credentials”; successful credentials load the workspace. Both widths fit cleanly. The shared form disables its fieldset while busy and uses a generic Saving label; a sampled runtime delay check landed after completion and is not evidence of a duplicate-submit defect.

The administrator browser bypasses this profile PIN by current server policy; that is not a reproduced authorization bypass. Browser account authentication remains distinct from TV device pairing/PIN. No native keypad, remote or emulator claim is made.

## Ranked findings

- **AUTH2-01 · P2 · bug — successful authentication followed by startup failure leaves a misleading sign-in screen.** `/api/auth/browser` succeeded, then injected `/api/playback/startup` 503 left Welcome back/Sign in with “Synthetic playback startup unavailable.” Reloading immediately entered the authenticated workspace. Browser credentials/session already existed, but local account state was not committed because startup was awaited first. Separate “Signed in; preparing playback” from credential validation and provide retry/recover without another password submission; ensure intended startup safety is completed before playback. **Accept:** credentials success/startup failure has explicit authenticated recovery, no duplicate login/session creation, and reload/retry behavior is coherent.
- **AUTH2-02 · P2 · bug/refinement — wrong PIN retains submitted digits.** Live wrong-PIN attempt retained four masked characters and required manual replacement. Clear rejected digits and return focus to PIN entry, keeping the error visible/announced. Distinguish network uncertainty so retry semantics remain intentional. Add concise “4–8 digits” help; the field enforces the pattern but does not explain it. **Accept:** wrong PIN clears digits; a valid six/eight-digit PIN waits for explicit Unlock/Enter; changing profile/screen discards the previous digits; rate limits have readable recovery guidance.
- **AUTH2-03 · owner request check (GLO-08), not reproduced.** After entering a username, following Server and TV setup instructions did not invoke a browser dialog in the observed run (`helpPrompt: []`). The shared form has a draft guard in source, but that alone is not evidence of a user-facing confirmation defect. Retain this live result; do not add a page bug solely from the generic implementation. If pending navigation later needs confirmation, keep its wording precise and never persist submitted secrets as drafts.
- **AUTH2-04 · P2 · additional UX — distinguish connection failure from logged-out state.** Auth/me 503 falls into Welcome back with an alert below setup help. Provide a prominent connection-error/retry state and keep sign-in available deliberately rather than treating transport failure as known logout. **Accept:** 401 shows sign-in, delay shows Connecting, offline/503 exposes Retry connection and server-help, and retry rechecks the existing session before requesting credentials.
- **AUTH2-05 · P3 · additional UX — improve credential task language.** Use Signing in / Unlocking profile for pending actions and a discoverable password visibility control with clear accessible state. Keep username autocomplete and masked default. **Accept:** task-specific busy feedback, duplicate submission blocked, visibility does not change field value or submit the form, and keyboard focus remains predictable.

No P0/P1 confirmed. Bootstrap, lockout expiry, credential reset, signed-out deep-link authorization and native PIN behavior need their own bounded checks; this pass does not claim exhaustive security verification.

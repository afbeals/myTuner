# Updating programming for paused and behind-live viewers

Research date: 2026-11-27. Project: `afbeals/myTuner`, local 0.3.1 follow-up on `feature/channel-empty-programming-delete` (schema 21 at inspection).

Research baseline (implementation is now owner-authorized). This agent read repository instructions, source and existing tests. It did not edit application/test/repository documentation, execute tests or servers, install/download tools, access household data/media, open screenshots, contact external services, commit, push or deploy. The parent has separately received owner authorization to implement after research; the recommendations below are not evidence that implementation has passed.

## Recommended outcome

A paused or behind-live viewer should eventually follow the channel's authoritative updated schedule, without an unexpected jump in viewing position. Finish that viewer's current complete airing, including its original mid-rolls, resumed program segments and associated following break. Then adopt a compatible authoritative revision at the same schedule timestamp. Preserve the session's position/anchor and therefore its delay; do not silently Go Live.

The recommendation is a small persisted per-session handover, staged when programming is published, plus bounded delivery at the handover boundary. It references shared schedule revisions rather than copying or rerolling programming per viewer. The browser and TV should show an accurate Next program from the handover target and reconcile delivery once at the natural boundary.

### Essential product distinction

Receiving the updated **channel timeline** does not mean applying today's settings retroactively to the next historical episode a delayed viewer watches. A viewer thirty minutes behind sees the same broadcast thirty minutes later. If an edit becomes effective in the broadcast at 21:00, that viewer encounters it around 21:30, unless they pause again. Their next personal airing at 20:45 may still use its original settings.

A new revision contains the authoritative old prefix before its broadcast publication boundary. It is safe to adopt that prefix before the revision's `effective_ms`; the new commercial rules still begin at their actual broadcast time. This avoids postponing a delayed viewer's revision adoption indefinitely when edits are frequent.

An already-diverged legacy session is different. If its old schedule says show A ends at 20:20 but the canonical timeline is in the middle of show B at 20:20, all three guarantees cannot be satisfied simultaneously: keep exact delay, finish A, and start B from its beginning immediately. Do not hide this limitation behind a revision-ID substitution. Prefer explicit recovery to the current broadcast for this exceptional upgrade case, unless the owner deliberately selects a delay-changing whole-program recovery policy.

## State and algorithm

### Minimal persistent additions

Use session columns or a one-row-per-session table with cascading deletion:

- `pending_revision_id`: nullable foreign key to the target revision, verified to belong to the same channel.
- `pending_at_ms`: nullable integer schedule timestamp; both pending fields must be present or absent together.
- Recommended `timeline_version`: monotonic integer incremented when a handover is staged/replaced/applied/cleared or a control invalidates its delivery context. Existing revision/entry identity might suffice for initial delivery protection, but an explicit epoch makes stale negotiations, controls and out-of-order polls easier to reject consistently.

Store source revision implicitly in existing `revision_id`. Do not change the underlying clock on a normal handover. The effective-revision helper must use one sampled server time per operation and return the current/pending view without expensive catalog work. Keep a pure/shared helper module rather than a circular ProgrammingService ↔ PlaybackService dependency.

A schema migration is justified by durable pending state. There is no need for a per-viewer schedule table, copied media, source scan, FFmpeg generation, new service or external database.

### Stage in the same transaction as publication

After materializing the new revision and copied prefix, inspect the channel's existing sessions with a prepared/indexed query. Include paused sessions. For each session:

1. Compute P from pause/anchor at publication time. Logically apply any already-due pending transition before considering the new publication; repeated edits must not create a lost transition chain.
2. Find the current old entry at P. Resolve its complete program group and E=`MAX(end_ms)` using `(revision_id,program_id)`, not a source runtime or the current entry end.
3. Prove compatibility against the new authoritative prefix: same program ID and complete ordered semantic intervals (media ID, kind, start/end, source offset and scheduled fingerprint), ignoring regenerated entry UUIDs. Comparing only title/media ID or total duration is insufficient. Both ends and individual ad/continuation rows matter.
4. Prove E is a valid boundary in the target. Its next program starts at E, or it represents a deliberate empty/known gap state. Never switch into a commercial or middle of a different program due to an assumed shared endpoint.
5. Set pending target=new revision, pending boundary=E. E may precede the live publication boundary B or the new target's `effective_ms`; that is safe because the target includes authoritative history there.
6. If a pending transition already exists, keep its earliest proven safe E when replacing the target. Do not restart the countdown at every publication. Replace only when the new target preserves that same full source airing/boundary. Otherwise retain the previously validated target and let a later compatible adoption follow it.
7. Leave incompatible legacy/diverged sessions unchanged with a bounded explicit recovery status. An invalid optional migration must not turn a successful authorized channel edit into a destructive session reset.

Publication-time staging is important: lazy describe-only detection can miss the first divergence if no descriptor request arrives between the edit and the viewer passing the boundary. Add lazy staging for upgrade sessions when a compatible current airing can still be proved; it is a repair path, not the sole mechanism.

Do not call media inspection or produce per-viewer schedule extensions inside the publication transaction. Reuse the new revision's prefix and grouped interval reads. Compare repeated identical source-revision/program candidates once per publication, then apply small row updates per affected session.

### Resolve and apply

All session entry points should use one helper for effective revision and pending state: describe, pause/resume/Go Live, negotiate, manifest, segments, events/history, reporting and any relevant background policy.

- Paused with P<E: retain old revision/position/frame. Publishing or polling never unpauses the viewer or progresses P.
- Unpaused with P<E: serve the original complete airing and original associated commercials. Return pending metadata and an accurate Next from the target after E. Normal one-second UI polls remain; staging does not add an independent per-session timer loop.
- At P≥E: authorize the target context, atomically adopt target, clear pending and increment the epoch. Keep position/anchor unchanged. If the first poll is late, use its P, not E or now; this retains the existing viewing-delay model and ordinary network-latency semantics.
- Exact E is the target side of the start-inclusive/end-exclusive boundary. Repeated concurrent requests must observe one idempotent transition, using an expected source/pending/version guard or a short transaction.
- Resume recomputes only its normal anchor. Pause exactly at E must resolve a due handover consistently before freezing; do not leave a paused row referencing old nonexistent future. Go Live clears pending and uses the existing explicit live join rules.
- Target denied/unavailable: stop or show an honest unavailable/recovery state without granting access, playing substituted media or silently returning to obsolete future programming. Missing files preserve timeline time. Deliberately empty programming becomes idle after retained prefix, not an eternal old rotation or standalone ads.
- Server restart: load persisted pending state and evaluate against P normally. No in-memory-only promises/timers are authoritative.

The actual new settings remain attached to their broadcast revision at B. Adopting a copied prefix at E<B does not invent commercials in prior airings. All viewers continue consuming the shared persisted decisions, shifted only by their existing session delay.

## Delivery, async safety and accounting

Cap the old revision's HLS query and segment loop at pending E. Reject old-future segment starts at or after E, including requests from a previously issued manifest. Recheck pending/source identity and the cap after async filesystem/FFmpeg work and before returning cached/new bytes. An entire airing boundary is naturally an entry boundary; if legacy malformed rows cross it, reject unsafe output rather than encode a mixed interval.

Do not include the target's later rows under an old revision playlist identity. At E, clients should refresh/negotiate the new descriptor/playlist once. Return an additive pending/effective-boundary field if needed for client countdown, source clipping, telemetry flush and next metadata. Native/browser epoch or existing revision/entry identity must guard negotiations that complete after cutover. A stale old-media negotiation cannot install a source, audio track or subtitle response onto the new airing.

Consider an explicit bounded completion rule for an old final segment/event after the transition: only the exact prior revision/session and entries ending no later than E, within the existing small lookbehind and a short elapsed-time grace, with fresh profile/source/fingerprint checks. Do not make the entire previous revision a permanent media backdoor. Alternatively deliberately cancel old requests at E and prove clients recover cleanly. Keep the choice explicit and test it.

Delivered-event interval timestamps must remain on their original schedule axis. Do not remap old event IDs to copied entry IDs, reset counters or count a revision handover as another scheduled airing. Late final old-entry events need either the narrow authorized completion rule above or an explicitly documented bounded telemetry loss; silently failing all such events obscures commercial exposure. Cache keys already depend on media fingerprint/source offset/duration/audio (`streaming.ts:257–266`); do not add session IDs merely because revision references changed.

Direct original delivery cannot retract bytes already fetched, but client entry/boundary control must prevent playing beyond the original complete airing. Keep originals immutable. Exact audio/subtitle preferences should follow the existing per-profile preference resolution on the next media, not reuse the old file's raw track index. Paused picture/context must survive staging.

## Alternatives and tradeoffs

| Approach                                                                               | Assessment                                                                                                                                                                                                                                                             |
| -------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Remove the live-only equality and switch when latest `effective_ms<=P`                 | Too weak: repeated newer edits can continually move the tested boundary ahead; old/diverged current programs can be replaced midway. Also misses manifest lookahead and stale async requests.                                                                          |
| Immediately rebind a matching copied prefix                                            | Can preserve semantic source playback but changes entry/revision IDs mid-show, causing existing clients to reload, cancel HLS and reset tracks. Pending end-of-airing adoption fits the requested UX better.                                                           |
| Infer earliest divergence from revision history each poll                              | Possible with persisted lineage, but current schema has no parent revision link. Matching large future schedules or traversing all historical revisions per one-second poll adds avoidable CPU/SQLite work. It still needs delivery caps and retention/async handling. |
| One compact persisted pending handover                                                 | Recommended. Exact known boundary, restart-safe and small per-session state; publication stages it once. No source I/O or new per-viewer random choices.                                                                                                               |
| Start the next latest-revision program from its beginning and rebase the session clock | Possible explicit recovery for legacy divergence, but changes the viewer's measured delay and can skip/repeat canonical airings. Needs owner wording/policy selection; do not claim constant delay.                                                                    |
| Rerun newest settings after the viewer's old show on a private schedule                | Changes the one-shared-broadcast model, commercial scheduling/accounting and storage complexity. Outside this fix.                                                                                                                                                     |

## Phased implementation plan

1. **Contract, helper and migration.** Record the selected constant-delay/shared-broadcast policy and exceptional legacy behavior. Add pending state/constraints and optional timeline epoch. Implement pure boundary compatibility/effective-state helpers with bounded SQL and deterministic time inputs. Add migration/backward-null coverage before wiring delivery.
2. **Publication, clock and retention.** Stage in publication transaction; normalize existing due transitions during later publications. Use shared effective resolution for session controls/describe/Next. Preserve legacy live behavior and grants. Protect pending targets in cleanup and reconcile deletion/reset/restore rows. Verify empty programming and many successive edits.
3. **Delivery enforcement.** Cap old HLS at E, reject stale future segments before/after async work, resolve target at E, and implement the chosen narrow completion/event policy. Update negotiate identity fields if required. Exercise actual synthetic segment outputs and cancellation without changing cache sharing.
4. **Browser and TV integration.** Keep paused still/context, show an unobtrusive “Updated programming after this show” only if it helps; update Next accurately. Refresh at boundary, ignore old negotiations/captions/polls, retain sensible audio/caption preferences and existing controls. Add small pure native helper/JVM coverage if client logic grows. Preserve live guide as broadcast context and player Next as session context.
5. **Integrated verification and docs.** Use disposable synthetic media/database, scoped backend/API and real browser tests, comparison-mode desktop/narrow visuals and accessibility. Then type/format/build/compiled/runtime/version checks appropriate to changed files. Update API/database/scheduling/client/checklist/verification docs, clear old assertions about indefinite pinning, and list physical/native verification limits honestly. No new program/tool downloads or emulator resumption is implied.

## Remaining choices and limits

The owner approved investigating and subsequently implementing delayed schedule adoption while protecting the current show. The parent should state that edits are received at their original broadcast timestamps, shifted by the viewer's existing delay. If the intended meaning is instead “newest settings on the very next personal episode regardless of broadcast history,” that is a separate personalized-schedule product change.

Recommended legacy fallback is an explicit small recovery explanation and Go Live/rejoin option when exact compatibility cannot be proved. A delay-changing start-at-program recovery is a valid optional alternative requiring deliberate selection. Do not silently cut or rewind the current program. Decide narrowly whether final old segments/events receive bounded completion grace or are canceled at E; measure actual browser/Media3 behavior before claiming seamless transition.

Use additive descriptor fields and retain existing `apiVersion:1` when compatible; older native clients need verification against the new server boundary behavior. New fields alone do not prove old clients' buffered HLS behavior. No native/emulator/physical visual evidence was produced by this research. No HDD/shared-resource interference measurement or hosted-CI success is claimed.
